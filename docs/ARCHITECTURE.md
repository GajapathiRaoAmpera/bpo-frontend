# Architecture (frontend)

## 1. Overview
Next.js App Router UI for Ampera BPO. Holds no business rules: data, RBAC, masking and audit live in `bpo-backend`. Contract = backend OpenAPI.

## 2. Stack
Next.js 16 (App Router, TypeScript strict) · SCSS modules (Sass) · Radix primitives (shadcn-derived) · TanStack Query (data) · TanStack Table (tables) · Recharts (charts) · lucide-react · React Hook Form + Zod (forms) · openapi-fetch + openapi-typescript (typed client) · sonner (toasts) · Pipecat JS client (Phase 2).

## 3. Request flow
```
Browser ─ /api/v1/* ─> Next.js rewrite (next.config.ts) ─> BACKEND_URL/api/v1/*
         (same origin, so the backend's httpOnly cookie is sent automatically)
```
- `src/proxy.ts` (Next 16 replacement for middleware): no valid session cookie → `/login?next=…`; `/` and `/login` with a session → role landing page. It decodes the JWT payload **without verifying** it, only for routing; the backend authorises every API call.
- `(app)/layout.tsx` → `AppShell` loads `/auth/me` once (TanStack Query) for persona, role label and menu. `{children}` always renders (Cache Components: never hold a segment behind the session read); header and sidebar fill in when `/auth/me` resolves.
- Every page wraps its content in `<ScreenGuard screen="…">`, which shows "No access" for a screen outside the role's menu (UX only; the API would 403 anyway).

## 4. Structure
```
src/
  app/                   ROUTES ONLY: page.tsx = metadata + <ScreenGuard> + the view; layouts; globals.scss
    login/               public
    (app)/               signed-in shell; one folder per route
  views/<feature>/       one <name>-page.tsx per screen: composes sections, holds screen-level state
                         (not `src/pages`: Next.js would treat that as the Pages Router)
  components/
    <feature>/           sections/widgets of one screen + use-<feature>.ts (TanStack Query hooks)
    ui/                  Radix primitives (shadcn-derived, styled with SCSS modules)
    shell/               banner, header, sidebar, app shell, screen guard
    common/              page header, section card, error alert, empty state, pill, module pending
    ops/ · maker-checker/ · admin/   cross-screen pieces (data table, tones, approval panels, labels)
  hooks/                 use-me (session), use-voice-call (Pipecat JS client: WebRTC audio + live captions)
  lib/                   api client, nav map (screen → route/label/icon), format (INR/IST)
  styles/                _tokens.scss (CSS variables) · _mixins.scss (type scale, spacing, breakpoints, motion)
  types/api.d.ts         GENERATED by `npm run gen:types`; never edit by hand
proxy.ts
```
Every `.tsx` with styling has a co-located `<name>.module.scss`.

## 5. Rules
- Types come only from `src/types/api.d.ts` (regenerate after backend changes). Never copy types from the backend.
- The access matrix is not duplicated: menu = `/auth/me` nav; `lib/nav.ts` only maps screen keys to route, label, icon.
- All money/date output through `lib/format.ts`.
- Server state through TanStack Query; no ad-hoc `fetch` in components.

## 6. Key decisions
| Decision | Reason |
|---|---|
| Session loaded client-side | `cacheComponents` is on; avoids dynamic `cookies()` in layouts; proxy already blocks anonymous users |
| Unverified JWT decode in proxy | Routing only; no JWT secret in the frontend |
| `output: "standalone"` | Small Docker image |

## 7. Voice (Phase 2)
`/agent-console` uses `@pipecat-ai/client-js` + `@pipecat-ai/small-webrtc-transport`, signalling to `/api/v1/voice/sessions/{id}/offer` through the same-origin rewrite (cookie auth). The API session (polled) is the source of truth for transcript, tool actions and summary; the client adds audio playback, mic level and live captions, and server messages trigger an immediate refetch.

## 8. Failure behaviour
- API 401 anywhere → redirect to `/login`.
- API down → error state with retry on the page; shell shows a sign-in error on `/auth/me` failure.
